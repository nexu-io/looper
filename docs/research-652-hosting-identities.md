# Hosting identity authentication and verification research

Research for issue #652, checked on 2026-09-12. This records external contracts and a proposed evidence path; it does not prescribe configuration field names. No live mutations were performed during this research.

## GitHub App contracts

- Sign App JWTs with RS256. The issuer can be the App ID or client ID; GitHub recommends the client ID, but the issue's agreed App ID input is supported. Backdate `iat` by about 60 seconds for clock skew and set `exp` no more than 10 minutes into the future. Send JWTs as `Authorization: Bearer`. [GitHub JWT documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)
- Exchange the JWT at `POST /app/installations/{installation_id}/access_tokens`. Installation tokens expire after one hour. Refresh means minting another installation token, not using the user-OAuth refresh-token flow. The response supplies `expires_at`; repository and permission restrictions can only narrow the installation's grants. Do not assume token length or parse its format: GitHub documents a rollout of longer stateless installation tokens beginning in April 2026. [Token generation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)
- Installation API actions are attributed to the App. REST and GraphQL are supported subject to endpoint permissions. HTTP Git authentication uses username `x-access-token` and the installation token as password, with the Contents repository permission. The documentation's credential-bearing URL is an authentication example, not an appropriate stored remote for this feature. [Installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)
- REST `GET /user` does **not** accept installation tokens. Public `GET /users/{username}` does. For App identity, use App metadata / the bot account, or the documented GraphQL `viewer { login }` query. Authentication failure must not become an empty identity. [Users API token types](https://docs.github.com/en/rest/users/users#get-the-authenticated-user), [installation GraphQL example](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)
- GitHub's own App-token action documents bot login as `<app-slug>[bot]` and GitHub.com commit email as `<bot-user-id>+<app-slug>[bot]@users.noreply.github.com`. Obtain the numeric **bot user ID** from `/users/<app-slug>[bot]`; neither the App ID nor installation ID is that ID. Setting Git author/committer is separate from authenticating a push. [Official App-token action: Git attribution](https://github.com/actions/create-github-app-token#configure-git-cli-for-an-apps-bot-user)
- `gh` uses `GH_TOKEN` before `GITHUB_TOKEN` for GitHub.com and `*.ghe.com`, overriding stored authentication. GitHub Enterprise Server uses `GH_ENTERPRISE_TOKEN` before `GITHUB_ENTERPRISE_TOKEN`. Bind the target host as well as the token; ambient `GH_HOST`, `GH_REPO`, credential helpers, and personal remote authentication must not redirect an explicit bot operation. [GitHub CLI environment](https://cli.github.com/manual/gh_help_environment)
- GHES REST URLs use `https://HOSTNAME/api/v3`; Git URLs remain on `https://HOSTNAME/owner/repo.git`. The GitHub.com bot email formula above was verified for GitHub.com only. An authoritative GHES bot noreply formula was not established in this research; do not silently claim the GitHub.com domain establishes attribution on GHES. [GHES installation API](https://docs.github.com/en/enterprise-server@3.20/rest/apps/installations)
- GitHub Enterprise Cloud with data residency is distinct from GHES: web origin `https://acme.ghe.com` maps to API origin `https://api.acme.ghe.com`, without `/api/v3`; GitHub's official example is `https://api.octocorp.ghe.com`. `gh --hostname` still uses the web hostname. Treat the GHE.com bot noreply formula as unverified and use an explicitly configured commit email or an authoritative returned address. [Cloud API access](https://docs.github.com/en/enterprise-cloud%40latest/admin/data-residency/about-github-enterprise-cloud-with-data-residency), [GHE.com CLI hostname](https://docs.github.com/en/enterprise-cloud%40latest/admin/data-residency/network-details-for-ghecom)

## Review discovery and permissions

- Current GitHub GraphQL documentation includes `Bot` in `RequestedReviewer`, along with `EnterpriseTeam`, `Mannequin`, `Team`, and `User`. `RequestReviewsInput` includes `botIds`. Therefore, neither “all requested reviewers are Users” nor “Apps can never receive review requests” is a safe assumption. Read `... on Bot { login }` where requested-reviewer identities are extracted. Actual eligibility of the configured App and `review-requested:<bot-login>` search must be verified on the sandbox; schema membership alone does not establish those behaviors. [RequestedReviewer](https://docs.github.com/en/graphql/reference/pulls#requestedreviewer), [RequestReviewsInput](https://docs.github.com/en/graphql/reference/pulls#requestreviewsinput)
- GitHub CLI documents `--review-requested` as a user/team filter. Test the concrete existing GraphQL search and query fields rather than treating CLI syntax acceptance as evidence of bot discoverability. [GitHub CLI PR search](https://cli.github.com/manual/gh_search_prs)
- Review creation supports installation tokens with Pull requests write permission. Issue-comment endpoints require Issues or Pull requests permissions as documented per operation. The repository's existing sandbox contract specifies Metadata read, Issues read/write, Pull requests read/write, Contents read/write, limited to the sandbox repository. Additional operations, such as workflow-file updates or checks inspection, need their own endpoint permissions; do not infer all capabilities from successful token minting. [Review API](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request), [Issue comments API](https://docs.github.com/en/rest/issues/comments)
- Separate identity support does not resolve the shared-identity policies in #598, #602, and #603 automatically. They respectively concern self review assignment/discovery, self-approval fallback and auto-merge, and exclusion of self-authored review comments. Acceptance evidence should exercise same-bot role reuse as well as a reviewer override, without changing these independent policies implicitly.

## Forgejo contracts

- Dedicated-account API tokens are accepted in the Authorization header. Keep the existing `Authorization: token ...` scheme for compatibility. Tokens can be created in the account's Applications settings; the token-creation API is a special password/Basic-authenticated endpoint and is not required for daemon operation. API compatibility is defined within a major Forgejo version. [Forgejo API usage](https://forgejo.org/docs/latest/user/api/usage/)
- Token scopes group routes: `write:repository` covers repository and PR operations; `write:issue` covers issues, labels, comments and related operations; `read:user` covers identity lookup. Forgejo v15+ repository-specific tokens allow only repository/issue scopes. Therefore, a token restricted to specific repositories cannot satisfy a mandatory `/api/v1/user` lookup. Either explicitly document the supported token setup with `read:user`, or deliberately design a separately verified account-identity input for restricted tokens. Do not silently fall back to tea. [Forgejo token scopes](https://forgejo.org/docs/latest/user/authentication/token-scope/)
- The current upstream router places `GET /user` in the user-scope group. The current access-token authentication implementation supports tokens in HTTP Basic authentication and resolves the account from the token's stored UID, independently of personal SSH state. Use HTTPS token authentication and preserve the original remote. [Forgejo API router](https://codeberg.org/forgejo/forgejo/src/branch/forgejo/routers/api/v1/api.go), [Forgejo token authentication](https://codeberg.org/forgejo/forgejo/src/branch/forgejo/services/auth/method/access_token.go)
- Query the actual instance's `/api/v1/version` and `/swagger.v1.json` when a version-specific behavior matters. The public documentation currently describes v16; older supported deployments may differ. No Forgejo Authorized Integrations/JWT behavior is needed for this issue.

## Existing repository affordances and gaps

The initial audit used `647ae4f9`; implementation moved to the latest main baseline `c610a504`. The authentication boundaries below are unchanged between these commits.

| Existing affordance | What it proves / remaining gap |
| --- | --- |
| `internal/e2e/githubcontract/contract_test.go` and strict fake `gh` | Command/schema contracts without real GitHub; suitable for propagation, token-selection, and denied-operation tests. It cannot prove real App scope semantics. |
| `internal/e2e/forgejocontract` | Forgejo API requests against strict fake boundaries; suitable for concurrent provider/identity isolation. |
| `internal/e2e/invariant_worktree_test.go`, fake agent, real local Git | Worktree lifecycle, author/committer, original-remote preservation, and agent credential absence can be deterministic integration claims. |
| `internal/e2e/github_sandbox_test.go` | Existing real worker PR, fixer thread, and no-diff cases with run-scoped resources and cleanup. Existing helper consumes an already minted token; it does not establish daemon JWT minting or refresh. |
| `.github/workflows/sandbox-e2e.yml`, release and cleanup workflows | Existing sandbox App registration and private-key secret; `actions/create-github-app-token@v3` mints a repository-scoped token. Use the action's installation-ID output or an explicit sandbox installation ID for a daemon-minting test. |
| `internal/e2e/forgejo_sandbox_test.go` | Local opt-in real Forgejo tests. Current prerequisites already call `/user`; required token scopes include `read:user`. |

Important baseline hazards to account for when reusing these helpers:

1. `internal/infra/github/gateway.go` has differing unsupported-`/user` behavior: `GetCurrentUserIdentity` and `GetCurrentUserLoginForRepo` use GraphQL fallback, while `getCurrentUserLoginRaw` returns an empty login. The identity-aware path must produce the configured bot identity or an explicit error.
2. `internal/infra/github/discovery_snapshot.go:300` caches current-user login by `cwd` only. Different role identities sharing a repository path must not share that cached actor. Isolate snapshots/gateways per identity session or include the identity boundary in cache keys.
3. `fixerSandboxConfig` currently injects `GH_TOKEN` into `agent.env` so the fake agent can read review-thread snapshots. A new bot-mode case must use daemon entry points and assert absence of bot credentials in the fake agent.
4. Both sandbox clone helpers currently construct token-bearing remote URLs. GitHub also puts a Basic Authorization header into command arguments. `runSandboxCommandMust` prints failed arguments, and persistent E2E artifacts can contain cloned configuration. Do not reuse those credential-bearing remotes/arguments as the new bot-mode verification path; a successful push alone would conceal the exact leak this issue must prevent.
5. `requireSandboxConfig` calls global `gh auth status`. That checks all known hosts/accounts unless constrained; unrelated expired personal credentials can produce a false prerequisite failure. Prefer a target-scoped API capability check, or `--active --hostname` where appropriate. [GitHub CLI auth status](https://cli.github.com/manual/gh_auth_status)

## Initial verification recommendations

| Claim | Owner and minimum evidence |
| --- | --- |
| Inheritance and frozen role identity | Config/runtime implementation: table coverage for all five roles, plus one cross-component run that survives a config update and observes the same identity at discovery, claiming, daemon operations and Git. A subsequent run must observe the new config. |
| Token refresh without account fallback | Credential implementation: local HTTP server verifies JWT signatures/claims and installation endpoint, returns short controlled expiries, and observes same-identity refresh. Denied mint/refresh must affect only the selected identity while another identity succeeds. No hour-long live wait is necessary. |
| Git and secret boundary | Runtime/Git implementation: real local Git and fake agent verify fetch/push use daemon credentials, SSH and personal helpers cannot satisfy explicit bot mode, original remotes remain byte-for-byte unchanged, new commits use both bot identities, amend preserves author, explicit overrides work, and agent-visible config/env/output contain neither token nor PEM contents. |
| Real GitHub authentication and scope | Sandbox integration: configure the daemon with App ID, installation ID and private-key-file reference; exercise token minting, bot current-user lookup, HTTPS push, PR/comment/review attribution, required discovery query, and a token narrowed to read-only permissions that gets a clear denied write. Exercise GraphQL thread operations if their authentication path changes. |
| Legacy authentication and Forgejo | Contract integration: no-identity projects retain existing `gh`/tea behavior, explicit Forgejo tokens never fall back to tea, same daemon routes two providers and two independent bot identities correctly. Use existing Forgejo live opt-in only for unresolved instance-specific API/Git semantics. |

Run the repository checks after the final implementation: formatting, `go vet ./...`, `go test ./...`, and `go build ./...`. Focused E2E entry points are `go test ./internal/e2e/githubcontract ./internal/e2e/forgejocontract -count=1`, the relevant invariant cases, and `go test ./internal/e2e -run '^TestGitHubSandbox' -count=1` with explicit sandbox inputs. Disabled live tests are skips, not evidence of a successful sandbox run.

Keep any sandbox private-key file outside `LOOPER_E2E_ARTIFACT_ROOT`, mode 0600, and remove it after the test. Config/artifacts should contain references only. Assertions should report identity names, endpoints and resource URLs without credential values. The chosen sandbox must permit run-scoped issue, PR, review/comment and branch creation/cleanup.

## Available setup at research time

Only variable presence was inspected; no credential values were read or printed.

- Current process: all checked GitHub/Forgejo sandbox variables were unset.
- Existing GitHub live inputs: `LOOPER_E2E_GITHUB=1`, `LOOPER_E2E_GITHUB_SANDBOX_REPO` (legacy alias `LOOPER_E2E_SANDBOX_REPO`), `LOOPER_E2E_GITHUB_TOKEN`.
- Existing CI App setup: repository variable `LOOPER_E2E_GITHUB_APP_ID`, secret `LOOPER_E2E_GITHUB_APP_PRIVATE_KEY`. At the baseline, the workflow passed only the minted token to tests. This implementation adds a separate App scenario using the existing private-key secret and the action’s installation-ID output; see the configuration guide for its exact scope. The default CI repository is `nexu-io/looper-sandbox`.
- Existing Forgejo live inputs: `LOOPER_E2E_FORGEJO=1`, `LOOPER_E2E_FORGEJO_BASE_URL`, `LOOPER_E2E_FORGEJO_SANDBOX_REPO`, `LOOPER_E2E_FORGEJO_TOKEN`.
- Historical project notes mention a local ignored `e2e/.env`; this research did not inspect that file or assert that it currently contains usable credentials.

Unverified live claims are App reviewer-request eligibility/search behavior, actual installation permission grants, live daemon token minting, and GHES bot email attribution. Deterministic tests can establish local propagation and failure behavior but must not be reported as proof of these external claims.
