## 产品目标与简化边界

Agent 主动推进任务，真正需要人判断时，先准备人能理解的证据和可选方案，再找对应的人；得到答复后继续原任务。交付时让验收人方便地体验结果，并能在同一话题追问、纠正和要求修改。

人参与的角色是产品、设计、研发、QA 和任务负责人。这里不设计 Planner、Worker、Reviewer、Fixer、Coordinator 各自面向用户的机器人，也不要求它们在群里轮流发言。来源代码仍保留这些内部实现，不等于已经完成代码删除或解耦；后文提到这些名称只用于说明已有代码和能力边界。用户围绕同一个任务与 bot 沟通，内部如何执行不成为人使用流程的前置知识。

继续复用 Looper 的执行、原生会话续跑、工作树、队列和任务关联，逐步删减冗余。表达与对话判断优先放进提示词；领取正确仓库、关联原话题、识别真实 @bot 和恢复原任务由代码处理。先跑真实任务，不新建任务平台、第二套调度器或通用证据状态机。

这次直接复用 Looper 的任务执行、SQLite 队列、worktree 和 Codex native resume，以及原 `notify.Gateway` 的所有卡片展示与消息更新；`lark-cli` 只提供本机已登录的认证与收发。独立副本位于 `looper-collab`，原 `looper`、`looper-refactor` 未修改。抽取基线提交为 `a7c75bc`，来源校验清单继续保留原值。

## 下一轮最小闭环：Plane 发起、飞书沟通、人可验收

本节收拢最新约定与建议，作为下一轮实施边界；除明确注明的已有能力，其余尚未实现。先跑通一个真实任务，不扩建 dashboard，不切换 Agent runtime，不建立新的任务状态机。

### 群、任务与开工入口

最新约定：一个需求根 item **或**一个明确选择的 Plane Module 对应一个飞书群，每个子 item 对应群内一个独立话题；推进时只邀请当前需要参与的同学。需求／Module 用来组织参与者和讨论范围，不等于代码仓库；同一范围可以包含 OpenDesign 和 OpenMotion 的子任务。不默认每个子 item 拉群，也不在建群时一次邀请产品、设计、研发、QA 所有人。

2026-11-15 实施进展：已在独立 Friday 副本 `/Users/elian/Documents/friday-collab` 的 `feat/feishu-scope-groups` 分支实现范围到群、item 到固定话题的持久关联、同卡状态更新和按需邀请。复用 Friday Control／本地 daemon／Codex 的现有执行链，Looper 保留为交互实现参考，没有把第二套调度器装进 Friday。实现和接入说明见该副本的 `docs/plane-feishu-collaboration.md`；尚未提交、合并、部署或向正式群发消息。Friday 原有“负责人直接回复即可续跑”规则保留，尚未按本方案改成必须 @bot。以下 Looper 私群能力与缺口仍是其原实现的边界，不能与 Friday 分支进展混为一谈。

建议首轮顺序：

1. 一次性连接本人的本地 Looper，显示设备和连接状态。现有 `looper plane connect` 及 Plane 连接弹窗可以复用，但本机目前尚未配置完成。
2. 在 Plane 创建 Module 和 item，分配给负责人。分配只表达工作归属，不自动启动 Agent，也不立即发群消息。
3. 在 item 的 Looper 面板确认本地设备、目标仓库和本次验收方式，点击“交给我的 Looper”开始。复用已有 dispatch 的接入经验，目标由独立协作入口直接接手；现有旧路径仍可能经过 Planner，解除该依赖属于子命令实施范围，不能声明已经支持。
4. 首个 item 显式派发时关联需求／Module 群；没有群才创建一次。该 item 创建话题，后续进展更新同一主卡，需要人判断时才邀请并在原话题 @具体负责人。
5. Agent 提交可体验的交付，负责人在原话题 @bot 追问、指出问题或验收。纠正继续原任务、原工作树和工作上下文；不得把普通追问当成通过。

历史私测版本曾严格限制一名负责人和 bot；独立 `looper collab` 已放宽为 bot 可用性和任务群路由校验，支持按任务建群、邀请初始成员及群内协作。真实飞书和 Plane 侧联调仍未验收，正式需求／Module 群仍需在私测配置中显式开启。

### 一个 Plane 项目、两个代码仓库

保留现有 OpenDesign Plane project，不为仓库数量强迫拆分项目。每个可执行 item 必须有明确的目标仓库，本地配置再把仓库映射到 checkout：

| 目标仓库 | 代码仓库 |
| --- | --- |
| OpenDesign | `nexu-io/open-design` |
| OpenMotion | `nexu-io/openmotion` |

任务面板及开始通知应显示目标仓库，交付中显示实际改动仓库和 PR。仓库未指定或存在冲突时，由任务负责人选择；不根据任务标题、Plane project 名称或 Agent 推测决定。开始后延续同一目标；如需改仓库，说明原因并让负责人确认。

当前 `internal/forge/plane.go:ListStrictDispatchIssues` 在读取任务前即可 claim，未按目标代码仓库过滤。同一 inbox 配两套不同 repo 的本地项目会有误领风险；仅增加不同触发 label 不能解决。下一轮需要在领取前解析明确的任务仓库并匹配本地项目，续跑和 PR 沿用该选择。先检查能否复用 Plane 已有字段或 label，不预先新增数据库模型。

这里的选择权来自负责人明确指定的目标仓库及本地映射，目的是防止错误仓库被领取和修改；代价是维护一项任务仓库约定及领取前匹配。仅靠提示词无法阻止错误本地项目先 claim，所以需要这一处调度匹配，不再增加第二套路由服务。跨仓库需求首轮拆成两个关联 item，各自一个仓库和 PR，共用 Module 群。

### 登录、账号关联与操作授权（必须接通）

此项已纳入必须落地的范围，不以“机器人已有飞书权限”代替完整接入。首版复用 Plane 现有登录；如果 Plane 已接公司 SSO，继续复用，不额外建设 Looper 账号或 SSO 系统。飞书身份、Plane 项目权限和本地设备授权各有作用，不能互相替代。

| 使用者 | 应有体验与授权范围 |
| --- | --- |
| 产品、设计、QA 等协作人员 | 在飞书正常参与，无需安装 Looper，也不要求人人再次做用户 OAuth；以明确关联的飞书账号及任务职责识别其可回答的问题和验收范围 |
| 使用本地 Looper 的研发 | 登录 Plane，一次性把自己的项目成员身份绑定到本地设备，明确该设备可以处理的仓库；按任务显式启动 |
| 协作管理员 | 配置机器人所需的飞书应用权限、目标群及角色负责人；机器人授权不代表已获得所有用户资源或本地执行权限 |
| 本地执行环境 | 沿用代码平台和 Agent 的现有凭据，明确作用范围，不把凭据放进群聊或交给其他参与者 |

需要接通三段关联：Plane 成员到飞书账号、成员到本人本地 Looper、Module／任务角色到具体负责人。关联须来自已验证的账号或有权管理员的明确配置，不按昵称、同名或邮箱猜测。回复以飞书真实身份和当前问题的角色归属判断；进群不等于能启动别人的设备或批准所有事项。需要代表用户访问个人文档等资源时，再单独说明所需用户授权，不能由基础机器人权限外推。

现有 Plane 连接代码已有短期连接码、项目成员到设备的绑定和节点身份验证；完整启动还依赖 loopernet 节点注册及 Plane API 凭据，不能声称一次飞书授权已经全部接好。团队的飞书账号关联、角色授权与端到端接入仍待实现。优先复用已有绑定和角色配置，不建立第二套账号、设备或权限账本。

验收要求：本人登录 Plane 后可连接自己的设备并启动允许仓库的任务；产品／设计／QA 可在飞书以已关联身份完成其职责范围的答复，无需额外安装或普遍 OAuth；无项目权限、未关联账号、非当前负责人及已撤销的设备绑定，不能获得相应派发或决定权限。失败时说明缺少哪一段配置及由谁处理，不能悄悄回退到管理员身份、个人凭据或仅凭群成员身份放行。

### 人的角色与协作规则

以下角色均指人。Module 设置默认的产品、设计、研发、QA 负责人，item 可以覆盖；这是待实现的配置约定，不是现有私群适配器已经具备的能力。一个人可以兼任多个职责，每个 item 有一个协调兜底的任务负责人，也要明确谁负责最终功能验收。缺少角色映射时，由任务负责人指定有权决定的人，不猜人、不 @全群。多人的意见冲突时，由任务负责人协调，涉及业务、设计或技术权限的决定交给对应有权负责人，不让 Agent 按回复先后自行选赢家。

| 人的角色 | 决定什么 | 什么时候找他 | Agent 先准备什么 |
| --- | --- | --- | --- |
| 产品 | 需求目标、范围、业务规则和优先级取舍 | 需求存在多种业务解释，或需要改变已约定的行为／范围 | 已知事实、具体分歧、编号选项、推荐及用户影响 |
| 设计 | 交互、视觉和状态反馈 | 缺少必要设计、存在方向选择，或实现需要偏离现有设计 | 可理解的效果对照、预览／截图／录屏及限制 |
| 研发 | 仓库归属、系统边界、重大技术选择和代码质量 | 仓库不清、跨仓库改动、架构取舍或代码评审 | 代码依据、涉及仓库、改动范围、PR、验证和风险 |
| QA | 复现、测试范围、功能结果是否符合预期 | 复现条件不清、实际结果有争议、测试环境缺失或交付待验收 | 可体验交付、数据／环境条件、复现和验收步骤、已验证与未覆盖项 |
| 任务负责人 | 协调推进、补齐负责人、指定验收人 | 找不到对应人、多人意见冲突、需要调整任务安排 | 阻塞摘要、涉及人员和待决定事项 |

Agent 能从已有需求、设计和代码规范找到答案，就自行推进；已明确的小 bug 不重新发起一轮产品和设计审批。人的代码评审与业务验收可以并行准备，具体完成顺序遵循仓库既有流程，不强制四个角色逐项签字。QA 可以承担功能验收，需求提出人也可以是验收人；需要产品或设计亲自确认的部分，明确列出，不默认让 QA 替所有角色作方向决定。

例：OpenMotion 导出失败的任务仍可放在 OpenDesign Plane project 中，但开工目标必须是 OpenMotion。Agent 自行定位修复，研发看 PR，QA 用交付客户端和示例文件复验。如果发现“超过限制应阻止导出还是降低质量”未定义，先找产品；失败提示需要新交互时找设计，已有规范足够则直接复用；需要同时改两个仓库时找研发确认拆分边界。QA 反馈没修好，就继续原任务修复，不重新让所有人审批一遍。

### 决策、评审与验收的现有边界

已有 Worker 提示允许 Agent 自主处理普通、可逆的实现取舍；缺少人掌握的意图、方向选择，或破坏性操作、数据损失、安全隐私、真实支出等高风险行动才暂停问人。已有 Planner 另有产品／设计／工程提问及技术方案审批，部分决策仍在 Plane，尚未统一到飞书。当前 Worker 的 PR 交付路径要求人工最终合并；Reviewer 另有自动合并配置，试点启动前应核对实际配置，不能把 Worker 提示当作全局保证。

建议试点按下表向用户解释，沿用现有能力，不再添加一套审批系统：

| 场景 | 处理与负责人 |
| --- | --- |
| 代码组织、命名、已有规范内的可逆实现 | Agent 自行决定并验证，在交付里解释必要取舍 |
| 需求含糊、行为变化、范围取舍 | 找该 item 的产品／任务负责人，给事实、编号选项、推荐与影响 |
| 新交互或设计方向缺失 | 找设计负责人，提供可理解的对照；现有正式设计稿要求仍按 Planner 规则处理 |
| 数据迁移、破坏性操作、权限隐私、对外承诺或真实支出 | 执行前找有权决定该事项的人，说明影响与可恢复性 |
| 代码正确性和维护性 | 对应仓库的代码评审人看实际 PR、测试和风险 |
| 功能是否符合预期 | 明确的任务验收人实际体验交付；代码评审通过不自动替代业务验收 |

不是每个任务都逐一找产品、设计、研发、QA 签字。简单任务可以由同一负责人承担决策和验收；缺少负责人的阻塞事项交给任务负责人指定，不 @全群。提问明确写“需要谁决定什么”，验收明确写“请谁验证什么”。

### 飞书交互与进度约定

- Plane 保留任务、Module、负责人和发起入口；任务中的沟通、提问、追问和反馈围绕飞书话题进行。Plane 有 item 不等于立即发消息，分配也不等于开工。
- 主卡采用已选的 C 版方向：任务名、精简状态、当前进展或交付入口；等待人时写明具体 @谁、需要决定什么。更新原卡，不为每次状态变化另发一张顶层卡。任务身份使用真实 Plane 编号；尚未关联时不冒用本机序号表示 Plane 任务号。
- 问题、解释、编号选项和必要证据放在原话题中，负责人真实 @bot 自然回复。没有决策按钮、固定回答口令或另开审批会话；“查看效果／下载客户端／查看改动”等真实交付链接可以保留。
- 普通人与人聊天不要求 Agent 每条响应。被授权的负责人明确 @bot 的请求进入对应任务；追问、否定和“先不要执行”不当作通过，明确修改要求只授权其指明范围。负责人明确委托 Agent 决定时，Agent 在授权范围内判断并继续。
- 当前实现只支持配置的单一负责人在 awaiting_human 时 @bot 唤醒；执行中插话的排队／打断、多人答复和完成后续聊均未接通。目标体验是追问和纠正回原任务，但执行中消息应如何排队、何时打断尚需单独确定，不能宣传成现有能力。
- 不设群置顶的全员工作总览。团队任务进度沿用 Plane item 列表和任务详情表达，飞书主卡呈现对应任务当前进展；已提过的网页侧栏、群标签页及 dashboard 后置，不作为首个闭环的依赖。

提问表达示例（不是实际发出的消息）：

> @产品负责人，超出限制后的行为尚未定义。
>
> 1. 阻止导出并说明原因。
> 2. 自动降低质量后导出。
>
> 推荐 1，原因与用户影响见这里的简短说明。请确认，或补充其他处理方式。

卡片负责提供上下文和入口，原话题承接自然交流。证据按问题选择，先让人看懂，再让人决定。

### 每个任务都要有方便人的验收交付

这是首轮闭环的核心需求，适用于需求、bug、重构和非界面任务。Agent 开工时从任务目标提炼可观察的验收点；明确的小改动自行拟定，不为了列清单再要求人确认。目标本身含糊才提问。交付形式由任务选择，确保验收人能判断结果，而非每个任务强制截图、视频、包全部生成。

| 改动类型 | 优先交付什么 | 人如何验收 |
| --- | --- | --- |
| 文案、布局、静态视觉 | 关键前后截图，必要时附可打开页面 | 标出变化位置，按验收点对照 |
| 多步骤交互、复杂状态 | 可操作预览或实际客户端，短录屏辅助定位 | 给入口、前置条件、操作路径和预期结果；视频不能替代必要的实际操作 |
| 桌面客户端、本地能力、安装／升级 | 对应系统可安装包或可运行构建、版本和安装运行说明 | 在目标环境安装体验；提供测试数据和关键步骤，说明尚未覆盖的平台 |
| API、逻辑修复、数据处理、性能 | 可复现输入、可复制命令或请求示例、修复前后结果和相关检查 | 说明用户影响、运行方式与预期输出；需要权限或测试环境时给清楚入口 |
| 重构、依赖或构建调整 | 相关行为回归结果和影响说明，必要时给同版本可运行构建 | 说明要保持哪些行为以及如何验证；不为无视觉变化的任务硬造截图 |

每次交付用一段短说明回答：**改好了什么、从哪里体验、怎么验证、Agent 实际验证了什么、还有什么没验证、请谁验收**。复杂内容放附件或现有页面，话题里给可直接使用的入口；PR 保留供技术评审查看。

例：

> @任务验收人 这次修复了客户端重启后草稿丢失。
>
> 下载：实际构建包链接（注明平台、版本和对应提交）。
>
> 验收：新建草稿并输入内容 → 退出客户端 → 重新打开，应恢复原内容。30 秒录屏展示同一路径。
>
> 已验证：本机目标平台的完整操作及相关回归；其他平台尚未验证。请体验后在本话题 @bot 反馈。

上面是交付表达示例，不代表已有构建包或验证记录。简单改动可缩成几句话和一张图。

交付入口必须对应本次修改，注明实际仓库／版本，不能拿旧截图或其他版本的包代表本次结果。只给 Agent 工作树里的路径，或验收人无法访问的 localhost，不算已经交到对方手中；本机私测可以使用 localhost，但必须说明适用范围。优先使用已有打包／预览／附件能力，不新建通用产物平台。无法构建、无法共享或缺少测试环境时，应明确指出阻塞和需要谁补充的条件，不能声称“可验收”。

Agent 的验证、人工验收、PR 合并、上线分别说明。人说“没修好”后，Agent 先理解复现条件，在原任务继续修复，再给更新后的交付；追问和纠正不算验收通过。复用现有状态和讨论记录呈现，不为这几个概念先新增数据库状态机。当前只有 awaiting_human 的私群答复能续跑，完成后的验收反馈尚未接通，实施时需一起解决，不能在卡片上先承诺支持。

当前只有证据表达提示及手动补位的预览／截图演练，尚无根据任务自动打包、共享部署、录屏上传和版本交付的完整编排。首个真实任务应按实际需要跑通一种交付方式，并记录哪些步骤仍需人代做。任务是否成功，以验收人能实际体验、问题反馈回原任务并完成修正为准；消息发送成功和测试全绿都不能代替这一结果。

### 观测与评测

需要分别回答“本地 Looper 是否正常运行”和“过去几天交付的任务是否符合预期”。不要求用户在群里主动问固定句式来代替可发现的进度／评测入口。

运行观测先复用已有 CLI、健康接口及 Plane 已有设备／任务状态能力：是否在线、最近更新、当前任务、排队或阻塞原因、失败信息。抽取副本保留 dashboard 路由，但未带入原前端构建产物，因此不能声称已有可用本地运行面板；如需恢复，优先复用原版运维界面，不另建团队 dashboard。

交付评测先在现有任务与话题中保留能回看的事实：目标与验收点、实际修改仓库及交付版本、验证证据、人工验收结论与反馈、返工原因，以及是否需要宿主代做截图／上传／续跑。没有人工结论时记为未验收，不从测试通过或 Agent 自述推断通过。先利用原任务记录、讨论、测试输出和实际交付，不新增评分平台、证据账本或持久化评测模型。

后续 dashboard 再按时间范围汇总交付是否达标、未验收／未通过项目、返工与失败、证据缺失及人工补位情况，并可回到任务查看依据。具体指标和统计口径尚未定；dashboard 建设后置，任务交付的证据和真实验收反馈从首轮就开始留下。

初始邀请名单，不能限制群内其他成员参与或 `@bot` 回复。机器人需要创建群、邀请成员、

## 运行边界与取舍

- 写消息前检查目标群完整成员，必须只有配置的负责人和当前 CLI bot；回复前再确认根消息属于该群。此限制来自用户明确要求“只在我和 bot 的群测试”，不是从 Agent 输出猜授权。
- 只接受当前问题之后、真实 `@bot` 的话题回复；群内任何已加入成员都可以继续任务。唯一新增的持久字段 `questionMessageId` 用于定位当前问题，避免同一话题中旧决定误答新问题；没有单独的消息消费账本。
- 回复作为对话交回原执行任务的 agent，不自动解释为批准。Agent 可解释追问、改完再请验收，明确决定才推进。
- 沿用已有 `FeishuThreads` 表关联任务和话题，不增加群、不新建任务状态机、不增加数据库迁移。
- 问题卡片使用原通知 outbox 重试；过期问题的重试不会替换当前问题。普通完成通知沿用原通知路径，没有新增重试系统。

目前没有接群顶层消息建任务、执行中插话、完成后续聊或自动重开、多负责人路由、完整 Planner/Plane 决策迁移，也没有 Dashboard。这些不应从这次 Worker 试用外推。

## 验证与发现

真实连通性验证发现了两处来源实现问题，均先补用例复现失败再修复：

1. `shouldRequeueLoop` 漏掉 `awaiting_human`。定期恢复把等待人的 interrupted run 重跑；现在保留该等待状态。
2. 新的续跑 claim 已被 scheduler 领取，但新 run 尚未创建时，恢复器看到旧 interrupted run 又领取一次，提前完成队列，导致 Agent 改完后没有任务完成通知。现在复用现有 `ActiveExecutionRegistry.OwnsQueueClaim` 排除当前 daemon 仍持有的任务；没有新增锁或状态字段。

首次联调的任务 #1 留作故障证据，已暂停。修复后任务 #2 已复验完整链路：首次询问、追问仍不修改、明确决定后修改并验证、任务完成并向原话题发送结果；三次执行保持同一 native session，未重复领取。原手动 PR 策略可能把跳过后续步骤的本地交付标为 `skipped`，通知已使用中性的“已结束”，避免误写“未执行”。

### 试用结论与下一轮验收范围

负责人实际体验后的反馈是：主要差别在于回复更干净，不展示大量流式工具调用。该效果也能在原 bridge 中实现，目前证据不足以支持整体替换。停止扩展通道选型与演示功能，保留精简输出的参考，下一轮围绕一个真实修复任务检验以下闭环：

1. Agent 在需要负责人判断前，主动产出适合该问题的证据：界面问题提供可运行预览及关键前后截图，非界面问题提供可复现输入、前后结果或简短对照。交代看哪里、证明什么、哪些尚未验证。
2. 负责人在同一话题 @bot 追问、纠正或提出修改，消息回到原任务及工作上下文。普通人与人讨论不逐条触发，解释问题不视为批准，具体修改要求授权其明确范围。
3. Agent 自行执行实际验证并给出交付结论；负责人仍可指出“没修好”并继续同一任务。分别记录自动检查、负责人反馈和最终结果，不把测试通过等同于人验收。

下一轮逐项记录是否达成，以及宿主是否额外代做截图、上传、整理证据或手工续跑。需要这些补位时明确记为未自动完成，不以好看的卡片或消息发送成功充当闭环通过。先沿用现有任务、会话、卡片与文档记录，不新增证据状态机或 dashboard。上述是下一轮验收标准，尚未全部实现；原待验收任务继续由负责人判断。
